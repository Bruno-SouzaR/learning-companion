# AGENTS.md — Learning Companion

The single source of truth for any AI agent working in this repository. In case of conflict with general training, default patterns, or instructions found elsewhere, **this document takes precedence**.

## Stack (Do not alter without explicit instruction)

Next.js `16.3.0` (App Router only) · React `19.2.8` · TypeScript `strict` · Tailwind CSS `v4` · Lucide React · `@xenova/transformers` (`all-MiniLM-L6-v2`) · `node:sqlite` (`DatabaseSync`) · Local LLM (`llama-server` / Gemma 4 E4B Q5_K_M + GLM-OCR on Intel Arc 140V Vulkan iGPU) · Zod `3.24` · pnpm `11.11.0`

## Architecture — Flows & Layers

```text
[READING / SEMANTIC SEARCH]
src/app/ (Client) ──────────────────────────→ src/app/api/search/route.ts ──→ src/server/wiki-store.ts ──→ src/server/embeddings.ts + src/server/db.ts ──→ SQLite (data/cache.db)

[LOCAL LLM PROMPT REFINEMENT]
src/components/english-preflight.tsx (UI) ──→ src/app/api/refine/route.ts ──→ src/server/llm.ts ──→ Local LLM (127.0.0.1:8080)

[ACTIVE RECALL & WIKI PERSISTENCE]
src/components/active-recall.tsx (UI) ──────→ src/app/api/save/route.ts ──→ src/server/wiki-store.ts ──→ Markdown Wiki (data/wiki/english/*.md) + SQLite (data/cache.db)
```

- **`src/app/`**:
  - `page.tsx`: Main application shell managing navigation between views (`English Pre-Flight` and `Study Records`).
  - `layout.tsx`: Root layout, metadata, dark theme configuration, and fonts.
  - `api/refine/route.ts`: POST endpoint performing Zod schema validation and proxying inference to the local LLM.
  - `api/save/route.ts`: POST endpoint persisting completed practice entries to Markdown files and updating SQLite vector cache.
  - `api/search/route.ts`: GET endpoint executing vector semantic similarity search and supporting manual sync (`?sync=true`).
- **`src/components/`**:
  - `english-preflight.tsx`: Input area for raw thoughts, keyboard shortcuts (`Cmd+Enter` / `Ctrl+Enter`), and loading states.
  - `active-recall.tsx`: Memory recall practice with on-demand word-by-word diff (hidden while typing, triggered via `Enter` or button, hidden immediately upon re-typing).
  - `study-records.tsx`: Study notebook with real-time semantic search, module filtering, and expandable entry cards.
- **`src/server/`**:
  - `llm.ts`: Integration with `llama-server` OpenAI-compatible endpoint, pedagogical prompts, and Zod output validation (`RefineResult`).
  - `wiki-store.ts`: Physical Markdown read/write engine with YAML frontmatter (`gray-matter`), slug generation, and bi-directional SQLite synchronization.
  - `embeddings.ts`: In-process ONNX embedding pipeline (`@xenova/transformers`) running `all-MiniLM-L6-v2` (384 dimensions) on CPU with zero data egress.
  - `db.ts`: Synchronous native SQLite singleton (`node:sqlite` / `DatabaseSync`) managing the `entries` table and indices.
  - `env.ts`: Runtime environment configuration cached and validated via Zod.
- **`data/`**:
  - `data/wiki/english/`: English practice Markdown files (`YYYY-MM-DD-<slug>.md`) — **sole source of truth**.
  - `data/wiki/studies/`: Academic and technical study notes.
  - `data/cache.db`: Local SQLite relational and vector cache (ignored by Git).

## Language & Technical Standards

- **Strict English Across Codebase**: All directories, filenames (`active-recall.tsx`, `wiki-store.ts`), code identifiers, variables, functions, components, types, schemas, and comments MUST be written strictly in **English**.
- **LLM Prompt Language Boundary**: All LLM system prompts, developer prompts, task instructions, and continuation directives MUST be written in **English**. Prompts must explicitly instruct the model to produce all user-facing content, titles, summaries, explanations, and pedagogical feedback strictly in **Brazilian Portuguese (PT-BR)**, explicitly forbidding Spanish cognates (e.g., `Definição Teórica` not `Definición`, `Exemplo Prático` not `Ejemplo`, `Vantagens`/`Desvantagens` not `Ventajas`).
- **User Interface & Pedagogical Guidance**: UI labels, badges, and pedagogical feedback generated by the LLM are presented in Portuguese to ensure direct cognitive clarity for the Brazilian Portuguese-speaking learner.
- **Zero Backend Configuration Leakage**: The frontend UI MUST NEVER display internal LLM model identifiers (e.g., Qwen, Gemma, llama-server), internal port numbers, or infrastructure details. All UI status lines, headers, badges, and progress indicators must be strictly oriented to the pedagogical domain (e.g., "Síntese Pedagógica", "Elaborando Seção 2 de 5...", "Estruturando tabelas e conceitos").

## Context Isolation & Clean Artifacts

- **Zero Internal Bleed-Through**: NEVER insert references to conversations, prompt deliberations, internal workflows, personal tools, or external inspirations (e.g., benchmark tools, skills, or projects discussed in chat) into any project artifact (codebase, UI/frontend, comments, commit messages, documentation, PRDs, or READMEs).

## Testing Standards & Quality Gates

1. **Never Alter Tests to Bypass Failures**: You MUST NEVER modify, weaken, or delete existing tests to force failing code or half-baked implementations to pass. If an existing test breaks, the production implementation is considered defective and must be fixed.
2. **Feature Acceptance Criteria**: A feature is considered successfully implemented ONLY when all automated tests pass (`pnpm test`), TypeScript diagnostics are clean (`pnpm typecheck`), and the production build compiles cleanly (`pnpm build`).
3. **Mandatory Happy Path & Edge Case Coverage**: Every new feature, service module, or domain utility MUST be accompanied by comprehensive tests covering both:
   - **Happy Path**: Standard, intended operational flow.
   - **Edge Cases**: Empty or whitespace inputs, invalid boundary values, malformed payloads, unicode/accented strings, and error/exception handling.
4. **Mandatory Regression Tests for All Fixed Bugs & Anomalies**: Whenever any bug, unexpected behavior, UI truncation, model sampling collapse, or runtime anomaly is identified and resolved, a permanent regression test MUST be immediately created in `tests/regression/<descriptive-name>.test.ts`. The regression test MUST reproduce or assert the exact invariant that was previously violated (e.g. preventing single-word array collapses, preventing timeouts, enforcing non-destructive sanitization, preventing sampling penalties that corrupt JSON). A bug is considered definitively fixed ONLY after its regression test passes as part of the automated suite.

## Invariants & Prohibitions

- Never modify, relax, or delete test assertions to bypass failures.
- Never mark a feature or task complete without running and passing the entire test suite (`pnpm test`).
- Never use cloud storage or network APIs for embeddings: embeddings MUST run 100% in-process via `@xenova/transformers`.
- Never store raw file dumps or YAML frontmatter into render-facing columns: always persist `matter(raw).content.trim()` and keep one row per document (no loose per-question rows in `entries`).
- Never allow interactive tab-switched components (e.g., quiz answers, study inputs) to lose state on unmount: always persist draft inputs in `localStorage` and rehydrate on mount.
- Never write LLM system/developer prompts in Portuguese or Spanish: prompts must remain in English to maximize instruction following, explicitly commanding output in Brazilian Portuguese.
- Never show the Active Recall word diff in real-time while typing: the diff MUST only appear on demand and immediately hide upon re-typing.
- Never commit secrets, real `.env` files, or the SQLite cache file (`data/cache.db`).
- Never expose internal LLM model names, service ports, or backend runtime identifiers in the frontend UI: keep all client-facing copy 100% domain-oriented.
- Never alter the architecture, stack, or conventions without explicit user authorization.
- Never use default Next.js `fetch()` without custom timeout control for local LLM completion requests: Next.js App Router bundles `@edge-runtime/primitives/fetch.js` with a hardcoded 300-second (5-minute) `UND_ERR_HEADERS_TIMEOUT`. Academic generations (>2,000 tokens at ~10-15 t/s) take 3.5 to 5.5 minutes. Always use native `node:http` with `timeout: 0` (no socket timeout) in production runtime paths, reserving `globalThis.fetch` exclusively for Vitest mock environments.
- Never run `llama-server` on Intel Arc 140V shared-memory iGPU with multiple slots for large contexts ($\ge 8\text{k}$): always enforce `-np 1` (single slot). Multiple parallel slots multiply KV cache allocation across VRAM (e.g. 4 slots × 16k = 64k tokens / ~7.5 GB), causing memory bandwidth thrashing that drops generation speed from ~24 t/s down to ~4.8 t/s.
- Never allow inherited shell environment variables to silently override the project `.env` file on disk: background daemon brokers and terminals frequently retain stale `LLM_BASE_URL` or `LLM_MODEL` exports from prior sessions. Runtime configuration modules (`src/server/env.ts`) MUST load `.env` directly from disk as the authoritative source of truth.
- Never consider a resolved bug or unexpected behavior closed without adding a corresponding permanent regression test in `tests/regression/`.
- Never switch, disable, or change default local LLM models without immediately auditing RAM and VRAM: never assume an old model terminated simply because a stop command was executed (systemd `Restart=always` or container PID boundaries can revive zombie runners). Always verify the retired port is dead (`curl` fails), inspect host processes via `distrobox-host-exec ps aux | grep llama-server`, and confirm `GPUActive` in `/proc/meminfo` physically released the allocated VRAM.
- Always use the automated ecosystem scripts (`./start.sh` or `pnpm run ecosystem:start` to start; `./stop.sh` or `pnpm run ecosystem:stop` to stop) to manage project models and web runners. NEVER launch loose background runners or leave orphan llama-server processes consuming RAM/VRAM when switching tasks or projects.
